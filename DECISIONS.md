# Checkout decisions

## 2026-10-18: Bun development and Workers Free production

The application uses pinned Bun 1.4.0 for local development, scripts, demo, tests, and dependency installation. Production uses Cloudflare Workers and its `workerd` runtime. This explicitly replaces the former Deno-only project rule; no Deno runtime, CLI, configuration, or deployment requirement remains. Node 24.20.0 is a narrow exception for Cloudflare's supported Wrangler/Miniflare control plane. The Bun test runner builds and launches that control plane when testing real workerd; application execution stays Bun or workerd.

The portable application remains in `main.ts`; `bun.ts` owns the Bun listener and durable local delayed queue, and `worker.ts` owns Worker HTTP, assets, and the exported SQLite-backed Durable Object scheduler. Worker services remain request-local and alarm services are reconstructed per invocation. The Worker import graph contains no Bun-only storage or TLS modules. The owner's final chain-webhook/no-cron decision below supersedes this migration's former no-Durable-Object prohibition and every cron or hosted interval policy, including Bun's optional maintenance interval. Containers, paid relays, and Docker remain outside this deployment.

## Persistence and compatibility

Production continues to use the existing `ubq-kv` Worker service, its D1 database, the `uos_checkout/v1` keyspace, and `CHECKOUT_KV_SERVICE_TOKEN`. No data copy, reset, database replacement, or signing-key rotation is part of this migration. Legacy raw JSON values remain readable. New writes use the versioned `uos_checkout_kv` envelope; every object and array is encoded structurally so arbitrary merchant JSON cannot collide with a nested bigint tag. Public token amounts remain decimal strings.

The shared service implements JSON values, CAS atomics, TTL, and prefix/cursor listing. The adapter treats HTTP 200 atomic conflicts as conflicts instead of transport failures. It fetches all prefix pages, decodes values, then applies typed tuple ordering, start-inclusive/end-exclusive ranges, reverse, and limit. Shared D1 LIKE patterns have a 50-byte bound: oversized derived prefixes fall back only to the wholly Checkout-owned `["uos_checkout", "v1"]` prefix before client filtering. This preserves current service behavior without changing the shared auth backend, at the cost of additional Checkout-only reads as that keyspace grows.

Local state uses Bun SQLite with transaction-backed CAS/versionstamps, snapshot values, expiry-as-absent reads/checks, and the same list semantics. `CHECKOUT_KV_URL` is a local SQLite path; service URL/token settings continue to select the hosted HTTP adapter for Bun.

## Webhook and ingress boundaries

Workers sends the original normalized HTTPS URL using native fetch, fresh application headers, `redirect: "manual"`, a timeout, and no incoming Host, credentials, or Cloudflare destination override. Public DNS prevalidation remains in place. The explicit `global_fetch_strictly_public` and `no_cots_on_external_fetch` compatibility flags enforces the actual connection's public destination after DNS resolution. Worker transport relies on platform TLS verification and does not claim to inspect or pin a peer address. A redirect is a failed delivery and never receives a replay of signed bytes. Response bodies are cancelled without unbounded buffering.

Bun retains hostname-verified TLS plus connected-peer comparison with the approved DNS result set before writing the HTTP request. Real local TLS tests cover trusted certificates, hostname mismatch, and peer mismatch with zero decrypted application bytes on rejection. Tests never disable certificate verification globally.

The Bun listener removes and rebuilds the internal local-peer marker from `server.requestIP()`. Both loopback peer and local HTTP origin are required for the development identity; a production hostname proxied over loopback remains authenticated normally. A Bun process behind the established local reverse proxy reconstructs HTTPS only when the actual peer is loopback, Host is exactly `checkout.ubq.fi`, and `x-forwarded-proto` is exactly `https`; this grants no development identity. The Worker strips the marker unconditionally, including on forged localhost URLs. Checkout retains its existing external Auth Hub origin/issuer pair; this runtime migration does not migrate that external authentication service.

## Maintenance and deployment contract

The owner rule is no cron, ever: no Deno.cron, Worker cron trigger/scheduled handler, setInterval sweep, low-frequency backstop, daily retention pass, or timer-driven repair in any Checkout runtime. Signed chain push is the primary payment detector; no payment-discovery schedule or chain-ingress drain alarm exists. Manual four-coordinate claims and `{}` invoice discovery remain immediate backups. The original expiry job owns one finite pass from invoice.minimumBlock to a captured upper head, using durable bounded chunks without ever extending that head. The first execution records startedAt; the pass stops after completion, three consecutive transient/no-progress attempts (progress resets the counter), or startedAt plus five minutes. The fixed safe, then finalized, then latest head snapshot uses 1000-block chunks without overlap and expiry_passes progress independent of manual discovery/reconciliation cursors. Thus an on-time pass ends by expiry plus five minutes, while a late/migrated invoice still receives one pass. A completion/attempt marker prevents a duplicate expiry wake from starting another pass. At the deadline or failure cap, expire any still-unpaid invoice and retain an explicit partial-coverage diagnostic; no full-range claim is made if the pass did not finish. This supersedes the old minute tick, chain/invoice rotation, discovery backoff and expired/reverted watcher proposals.

The provider-neutral chain-event processor is exposed through the Alchemy adapter at `POST /api/v1/chain-events/alchemy`. `CHECKOUT_ALCHEMY_WEBHOOK_KEYS` is a secret JSON map `webhookId -> {network, signingKey}`; each subscription is pinned to its network and unique literal UTF-8 signing-key bytes. The adapter accepts token/erc20 activity labels and one-to-nine-digit UTC timestamp fractions while retaining strict ERC20 log validation. Verify HMAC-SHA256 over the unchanged raw body against the hex X-Alchemy-Signature before receipt/domain access. Reject missing/invalid signatures, unsupported subscriptions/networks, malformed payloads, and stale/future payloads. The 256-KiB body and 256-activity admission caps are application limits, not documented Alchemy maxima. The createdAt window is at most 15 minutes old and 60 seconds future as application policy; official docs/source do not establish notification-time semantics, so compatibility with an old registered webhook requires owner live verification before claiming production acceptance.

Each transfer uses its own log transaction hash, log index, block number/hash, normalized token, recipient and integer amount. Matching uses direct amount-reservation and transaction-locator reads, with existing locator ownership taking precedence over a reused amount reservation. It retains minimum block, exact native-USDC amount, the invoice treasury snapshot and unpaid/reverted eligibility; canonical claim/refresh CAS governs duplicates, reinclusion and removed hints without invoice enumeration. Provider signatures authenticate a hint, not settlement or finality. Canonical verification is event-triggered and never becomes scheduled payment polling. Authenticate completed replays, then acknowledge the same subscription/event ID and body digest with HTTP 200 without repeating work; a conflicting body for the same identity returns 409. Incomplete or actively owned work returns 503 with persisted progress, and retries resume only unfinished items. A received batch never loses an acknowledged suffix. Related-request recovery reads only the indexed current item, through at most eight pending references for that invoice match tuple; an unindexed batch suffix is not discoverable by that lookup. Startup or another related event can recover retained work, but elapsed time alone cannot start a repair timer.

`POST /api/v1/invoices/{id}/claims` accepts exactly `{}` or the existing complete four-coordinate body. Discovery searches only that invoice with the shared canonical match predicate and safe, then finalized, then latest head; it returns `{ invoice, eventJws?, discovery?: { found, searchedToBlock? } }`, with decimal-string progress. No match or bounded incomplete work is HTTP 200, and found reflects the returned current payment after refresh/reorg. Discovery has separate durable completed progress and never reads or advances a reconciliation cursor. Incomplete verification does not advance progress, and successful replay returns the current invoice/event identity. Invalid body shapes keep the existing invalid-input error.

Known-payment confirmation schedules a finite sealed, safe and finalized milestone set keyed to the payment/inclusion generation. Current local estimates from the canonical payment timestamp are Ethereum: 36 seconds, 768 seconds and 1152 seconds; Optimism: 6 seconds, 300 seconds and 1800 seconds; Base: 6 seconds, 120 seconds and 1200 seconds. These are expected scheduling times, not protocol deadlines or proof of phase. Canonical receipt, block hash and actual latest/safe/finalized heads decide every transition. A late safe check can use the already-planned final milestone; if the final check still misses, retain pending state/diagnostic and wait for a related authenticated request, chain notice or write. Do not periodically rearm on late/null heads. Stale callbacks cannot mutate a replacement payment or add more milestones.

Shared KV remains authoritative for invoices, payment/event records and discovery/receipt progress. Worker scheduling crosses two stores with a prepared intent: durably arm every target before the fenced domain/committed-intent CAS; cancel an uncommitted preparation by versionstamp CAS before dropping it, and retire a committed intent only after every target durably adopts. Replay preserves newer generations, earlier deadlines, progress, attempts and delivered state. Every continuation checks its durable operation/generation or lease after external awaits and before further I/O, completion or alarm changes; stale work cannot release a successor or overwrite a newer inclusion. No credential is stored in job, receipt, intent or DO storage.

Bun shares the pure job core with the DO adapter and uses the approved durable local KV delayed queue. The job and due-index entry commit atomically with the originating domain change. Each process startup hydrates committed jobs and makes one finite idempotent existing-domain adoption pass, preserving valid generations, leases, deadlines and expiry progress. This is per startup, not a permanent migration-complete marker. Enqueue/dequeue/delivery/startup and related request/write events refresh the queue head. One one-shot callback delivers the next known job at its due time, chaining that job's long delay if needed. It is neither a sweep nor timer-based recovery. A lost in-memory callback is recovered only by startup, a related request/write, or the work's originally registered alarm.

The first ordinary Worker request starts a one-time migration through bounded request slices, not a migration alarm. Persist phase, raw prefix/cursor, bounded page identities/next cursor and item offset; checkpoint only durable adoption and never advance past unarmed work. While migration is pending, ordinary application requests return HTTP 503 migration_pending before entering their handler; GET /api/health remains 200 and advances a bounded slice. The owner issues a finite GET health cutover batch until x-checkout-events-migration is complete. Even the slice writing the completion marker reports pending; the next entry-complete request reports complete with zero shared-KV migration work. HEAD is not the migration health path, and HTTP 200 alone does not prove completion. Use a bounded raw service-page API within the Checkout keyspace, not list(limit) that collects every page first. Adopt invoice expiry, finite known-payment milestone and undelivered outbox work including future retries; never synthesize payment polling or expired/reverted watchers. Completion stays quiescent. Verify chain webhook authentication before any KV-backed migration/recovery, so malformed or invalid-HMAC deliveries cause no storage work. Settle old unfenced writers before accepting coverage; if one could have written behind the cursor, trigger a fresh versioned migration event. Each Bun process startup hydrates committed queue jobs and runs one finite existing-domain adoption pass, even when a previous process completed its pass; valid existing jobs remain intact. This permits shared-KV reuse after Worker-created work without a permanent local completion marker or periodic scan.

Merchant event creation schedules one delivery job; failed attempts retain authoritative nextAttemptAt and backoff, delivered events cancel work, and renewed signatures retain event JTI. Durable attempt ownership suppresses concurrent duplicate wakes, but HTTP success can occur before its acknowledgment is recorded, so delivery after ambiguous outcomes is at least once and requires recipient deduplication; no physical exactly-once claim is made. Existing codec, legacy reads, shared keyspace/KV token, signing identity, admin/merchant authentication, public-egress transport and ingress trust remain in force. The inbound Alchemy secret is owner-provisioned setup, not an agent-created credential. History and lazy amount-reservation rules remain; no new purge or periodic retention job is introduced. Terminal invoice/known-payment/delivery/migration work leaves no scheduled activity.

Platform facts checked on 2026-10-18: Workers Free HTTP CPU is 10 ms, external subrequests are 50/invocation, service bindings have a 32-Worker-invocation ceiling, and account requests are 100,000/day. The DO-specific default is 30 seconds CPU, with 15-minute alarm wall time. Free SQLite DO allowances are 100,000 requests/day including alarms/RPC sessions, 13,000 GB-s/day, 5 million row reads/day, 100,000 row writes/day and 5 GB account storage; setAlarm writes one row. Preserve conservative budgets and completion headroom without a paid CPU override. Daily exhaustion rejects affected operations until 00:00 UTC; docs do not promise automatic overdue catch-up. Alchemy lists five Free webhooks and up to ten-minute Free/PAYG retry backoff for non-200 responses. Three required mainnet subscriptions fit only if account capacity is available. Admission caps, finite provider retries, partial expiry coverage and finite confirmation checks do not guarantee unattended completion; retained work may await a permitted related event, never polling.

`bun run check` covers Prettier, ESLint, both Bun and Worker TypeScript entry points, the isolated offline suite, real Bun ingress/TLS checks, and the real workerd harness with mocked storage/RPC/DNS/webhook upstreams. The harness does not write production state. `bun run test:anvil` is a separate networked demo acceptance requiring Foundry and pinned Base fork access. `bun run deploy:dry-run` verifies Worker packaging. Production readiness additionally requires the deployed public path, retained JWKS identity, authenticated API behavior, owner-configured chain delivery, and actual alarm/migration acceptance; build and mock evidence do not establish them.

The `candidate` environment has no routes or cron and needs its own non-inherited SQLite DO binding. Production targets only `checkout.ubq.fi/*` and the established `ubq-kv` service. CI deploys the `development` branch using the existing protected `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` credentials; the Checkout KV token and owner-provisioned Alchemy key map stay Worker secrets. Both production and candidate require the Alchemy secret, so the owner installs its map on the existing Worker before deploying this reviewed code; then a finite GET health migration must report entry-time complete before notification activation/cutover. Cutover must settle old unfenced/interval writers and verify event-triggered migration and owner-configured chain delivery. Retain a Bun release with the current codec as the reversible target until acceptance passes; no rollback may restore cron or a maintenance interval. The old adapter cannot read newly enveloped values and must not be restored after new writes.
