Payment detection is signed chain push at `POST https://checkout.ubq.fi/api/v1/chain-events/alchemy`. The provider-neutral processor uses the native-USDC amount reservation and own transaction locator, then canonical receipt/block verification. Each notice carries its own transaction hash, log index, block number/hash, token, recipient and bigint amount. Removed and changed-inclusion hints use existing canonical refresh/reversion; stale hints and duplicates cannot overwrite a newer inclusion. No recurring new-payment search remains.

The merchant's four-coordinate claim and `{}` invoice discovery remain immediate backups. Discovery returns the existing Prospector-compatible `{ invoice, eventJws?, discovery?: { found, searchedToBlock? } }` shape, including HTTP 200 for not-found/partial work and decimal-string completed progress. It never advances reconciliation cursors. Found is derived from the returned current payment; event signing/replay preserves lifecycle identity after reorg. Signed batch authentication precedes KV work; completed same-ID/hash replay ACKs 200 without processing, body conflict is 409, and incomplete/owned work is 503 with durable progress.

## Existing-state migration and owner cutover

Worker migration identity is `migration:checkout-events-v1`; it retains `checkout_migration_v1` phase/cursor/page/offset state in local DO storage. Each ordinary request reads at most one bounded raw service page (eight entries) and adopts at most two targets. It uses the current Checkout codec/prefix, checkpoints adopted targets before advancing, preserves current jobs, and covers original invoice expiry, finite known-payment work and undelivered outbox including future retries. It creates no payment polling or expired/reverted watcher.

While pending, ordinary application requests return `503 migration_pending` before the handler. `GET /api/health` remains 200 and advances a slice; HEAD does not substitute. Even the slice persisting completion reports `x-checkout-events-migration: pending`; a later entry-complete GET reports complete with zero shared-KV migration work. The owner runs only a finite cutover batch until that header is complete. An absent header or HTTP 200 alone proves nothing about migration completion. The chain route bypasses bootstrap and rejects bad signatures before KV; it is not a migration progress trigger. Settle old unfenced writers before claiming coverage, and trigger a fresh versioned pass if an old writer could have inserted behind the cursor.

Bun startup hydrates committed jobs and performs one finite adoption pass on every process startup, preserving already valid jobs/leases/deadlines/expiry progress. Thereafter only enqueue/dequeue/delivery/startup/related requests or writes refresh the queue head; one-shot callbacks deliver known work, chaining long delays for that same job. No elapsed-time-only repair is added.
