## Selected behavior and accepted foundations

Each payment-dialog invoice is an attempt with a distinct reserved amount; intentional creation is separate from an idempotent replay. The account is `(authenticated merchant ID, stored opaque customerReference)`, grouping unresolved attempts across products/chains while preserving immutable product/token/treasury/minimum-block snapshots. One-hour UI expiry does not resolve candidacy. Check-again `{}`, wallet coordinates, signed chain notification and new-attempt creation are event triggers for one logical account hunt through captured latest heads, not one 1000-block search per press. A new idempotency key creates a distinct attempt; replay keeps the original. New equal-time attempts have causal sequence ordering, while legacy createdAt ties remain protected.

The standard JSON-RPC 2.0 log array carries disjoint <=1000-block requests with unique IDs, correlates unordered results by ID, retains success, retries failed/missing/invalid entries once within the reserve and splits explicit size rejection within byte/entry/call bounds. An exact newly captured numeric head can require its own POST because batch entries cannot reference one another's results. HTTP/non-array failure fails the sent batch; never send an empty batch. Incomplete enumeration, exact failed/unsearched ranges and contiguous searchedToBlock remain explicit. A bounded implementation does not promise arbitrary-span completion or hide failed holes.

Canonical latest observations record confirming immediately. Actual safe/finalized evidence permits credit-bearing events; three sealed blocks grant no credit. Existing merchant/event identity, canonical reorg and idempotent fulfillment paths remain. The invoice-ID response keeps the requested anchor invoice and its actual discovery.found value with the legacy invoice/eventJws/discovery shape. Account coverage and per-attempt credited/confirming/nothing-yet/invalidated outcomes are additive, not new incompatible invoice.status strings. Current Prospector parsing drops additive data and its HTTP/browser projections require consumer integration before those outcomes are claimed visible; accepted fields and evidence are recorded below; current consumer projections still require separate integration for visibility.

Earlier unpaid attempts can be invalidated and active reservations released only with complete relevant enumeration/ranges, canonical verification and currentness fences; current confirming/payment-bearing attempts are protected. Permanent amount-ownership history remains after release. Ambiguous reuse across accounts is retained for manual review with no automatic credit to either account, while an exact existing transaction locator wins. Incomplete ownership reads stay unclassified. Relevant unmatched transfers are retained for review rather than silently discarded. This is the handoff-authorized release policy with a conservative global attribution guard, not an unanswered preference being treated as approval.

## Accepted runtime source contract

The accepted runtime adds accountHunt with complete, reachedHead, pending and diagnostics; attempts entries contain invoiceId, outcome (credited, confirming, nothing_yet or invalidated) and searchComplete; groups contain chainId, tokenAddress, treasuryAddress, optional decimal-string targetHead/searchedToBlock and reachedHead. Complete means this pass's covered observations/refresh/resolution work finished, not that every attempt was paid or invalidated. ReachedHead describes captured-range coverage, not canonical credit. Legacy discovery.searchedToBlock maps the anchor's chain/token/treasury group. Legacy found:false or nothing_yet is allowed with incomplete work; failed ranges cannot prove an attempt unpaid or authorize invalidation, and pending/coverage diagnostics must expose the gap. The source is accepted as a367c2f0ddaed247f757c84fcdd447f84e4504d3, integrated by9ce040ea3ecf16353ee69842a51e5043349d579f; final canonical review/CI/publication remain separate acceptance steps.

The runtime uses migration:checkout-events-v2 with checkout_migration_v2 phases invoices, accounts, outbox and complete. The accounts phase advances shared [uos_checkout,v1,payments,account_index_v1] state (complete/cursor/retained page IDs/next/offset). Account and ownership manifests use exact 64-entry account_pages/ownership_pages keys with account_membership revision/sequence/count and ownership_membership count controls; attempt_states stores internal resolution separately from invoice.status. Missing/inconsistent manifests are not complete coverage. Legacy adoption writes permanent ownership and treasury_history descriptors for all valid invoice snapshots, including invalidated/history addresses needed for late-transfer review. Bun performs one finite legacy adoption pass per process startup; Worker v2 completion must include the accounts phase, not reuse v1 as proof.

Runtime limits are Worker HTTP 30 charged slots, entity alarm 28, migration ensure 24 and nested adopt 7. Nested allowances are reserved INSIDE the caller envelope with completion capacity protected, not added after 30. The native manual HTTP ledger used 28 actual root calls (23 storage, 3 RPC, 2 bindings), leaving 2 slots. A separate HTTP row used 21 actual root calls plus a reserved 7-call nested upper bound, leaving 2; adding the entry yields a conservative bound of 29. Seven is a reservation, not observed nested traffic. The harness bounds actual calls plus reserved nested plus entry at32 and actual calls at50 across recorded contexts; printed detailed rows are HTTP only. Do not sum independent alarms or claim exact nested attribution beyond these bounds. Live CPU/quota capacity remains unproved.

Terminal invoice statuses alone do not prove global quiescence. A budgeted request can leave an unadopted COMMITTED wake intent for that target. Only the target's related request or its already registered original alarm advances bounded adoption/ACK/retirement; unrelated requests do not sweep other entities. Quiet is asserted after all legitimate jobs and per-target committed intents are adopted/retired, without a new cleanup timer or history deletion.
